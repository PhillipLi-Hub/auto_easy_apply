# Easy Apply desktop assistant

## Test REST API from your phone

Run `powershell -NoProfile -ExecutionPolicy Bypass -File .\StartTestAPI.ps1` from this folder. Keep the terminal open, connect your phone to the same Wi-Fi as your PC, and open the printed `http://<PC-IP>:8000/api/test` URL in your phone browser. It returns `{"ok": true, "message": "Hello from your PC!"}`. `/health` and `/` return the same response; unknown paths return JSON with HTTP 404.

If Windows Firewall prompts, allow Python on your trusted Private network. If the phone cannot connect, check that the network allows communication between devices (guest Wi-Fi often blocks it). This is an unauthenticated HTTP test service for a trusted local network; do not forward its port to the internet. It exposes no application data or controls. Stop it with Ctrl+C. Use `-Port 8001` on the launcher to choose another port. No extra Python packages are needed.

A local Windows desktop app for your own LinkedIn Easy Apply applications. It uses Tkinter and a visible Microsoft Edge browser controlled by Playwright. Your existing stock-backtesting project is separate.

## Daily schedule

After each scheduled or manual auto-apply run, **Daily reports** shows cumulative confirmed applications for each London calendar day. Counts cover Quant, Data Scientist, Software Engineer, Trader, Machine Learning Engineer, AI Engineer, Risk, and Other. Each job appears in exactly one category, based on its title; overlapping titles use the precedence documented in the report. An HTML report lists roles, companies, LinkedIn links and times. Matching JSON and count-summary CSV files are saved under `data/reports/daily/YYYY-MM-DD.*`. Multiple runs on the same day refresh that day's totals, without adding duplicates. Select earlier dates in the tab to view or regenerate reports.

Reports also generate for runs that stop early or hit the LinkedIn daily limit, with the outcome shown. Counts include only app-confirmed submissions, excluding jobs discovered as already applied, manual applied marks, and uncertain submissions. New confirmations use an immutable ledger and the recorded submission-attempt time; later status changes do not change the reporting date. Imported older app-confirmed records use their last saved update time, explicitly labelled **approximate historical dates**. An uncertain submission is counted only after confirmation. London time conversion includes daylight-saving changes, and runs spanning midnight generate a report for each affected day.

### Private web dashboard

Open **Daily reports → Open web dashboard** to view reports from your phone or another computer, using any internet connection. Sign in with the ChatGPT account that owns the private Site. **Sync dashboard now** retries an upload immediately.

While this desktop app is open, reports and a status heartbeat sync automatically every 60 seconds, with a sync requested after each operation finishes. The webpage refreshes every 30 seconds. It shows daily category counts, job titles, employers, LinkedIn links, run history, date/category/search filters and CSV export. Only confirmed applications are counted. Queue and attention counts represent the latest sync, not the selected historical date.

Uploaded history remains available when the PC is off. Updates older than three minutes are labelled stale; an old running/paused heartbeat is not treated as proof that the PC is still active. The webpage does not start or control applications. Offline uploads retry automatically without interrupting the application worker.

The connection is configured locally in ignored `data/dashboard.json`; its credential is protected for your Windows account in `data/dashboard_secret.bin`. CVs, saved answers, application notes, browser cookies and LLM logs are not uploaded. To disable uploads, set `enabled` to `false` in `data/dashboard.json`. Existing hosted reports remain private and readable. Never change the destination or share its service credential.

For a new installation, provision the sibling `easy_apply_dashboard` Site with owner-private access and its upload secret, then run `.venv\Scripts\python.exe -m easy_apply.dashboard_sync --configure`. This prompts for the Site URL and a hidden service credential. Do not put credentials in command arguments. `--sync` performs one upload; normal app startup handles ongoing uploads. Gmail setup is independent and is not required for the dashboard.

### Gmail delivery after the daily limit

In **Daily reports → Gmail setup**, enter your Gmail address and a [Google App Password](https://support.google.com/accounts/answer/185833?hl=en), enable automatic email, and choose **Save and verify**. Google requires 2-Step Verification to create an App Password. Enter it only in the app's masked field, not in chat or `settings.json`. The app encrypts it with Windows DPAPI for the signed-in Windows account; the scheduled task uses the same account. Leave the password field blank to retain it. The Gmail connection in ChatGPT does not provide credentials to this desktop process.

After an application run detects **LinkedIn's daily Easy Apply limit**, the app queues one report email per London calendar day and sends it to the configured Gmail address from that same account. Email contains category totals, confirmed roles and links, plus HTML and CSV attachments. A normal run ending at the app's configured submission cap does not trigger email. Sending uses authenticated SMTP with verified TLS at `smtp.gmail.com:587` ([Google's settings](https://support.google.com/mail/answer/7104828?hl=en-uk)).

The **Daily reports** tab shows delivery status. Missing credentials, authentication failures and pre-send connection failures leave a retryable report. **Save and verify** retries pending reports once sign-in succeeds, and **Retry pending email** can retry known failures later. A new daily-limit event also retries pending failures. Repeated daily-limit messages or restarts do not resend an accepted report. If the connection fails during sending, delivery is marked uncertain and automatic retry is blocked; check Gmail Sent before arranging another send. Disable the checkbox to stop email delivery. Local reports continue to be saved.

Run `powershell -NoProfile -ExecutionPolicy Bypass -File .\ScheduleDaily.ps1 -Time 09:00` to enable daily auto apply in Windows Task Scheduler. It runs at the computer's local time (including daylight-saving changes), using the latest **saved** profile, answers, limits, and job filters. The installer sets the first trigger in the future; it does not apply immediately. To disable it, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\ScheduleDaily.ps1 -Disable`. Restart the desktop after changing the schedule to refresh its schedule label.

The PC must be powered on and Windows signed in. The task requests wake from sleep (subject to Windows power settings) and checks again every 15 minutes and at sign-in to catch a missed launch. Checks before the configured start time do nothing. It cannot run while the PC is shut down. LinkedIn login or verification may require manual intervention. Each local calendar day gets at most one scheduled start; a busy app skips that start rather than launching overlapping applications. Closing or stopping a started run does not restart it that day. A pending request whose desktop failed to open can be delivered again. The existing app window handles the request, or the task opens one if needed. Task Scheduler may show Running while that desktop remains open; tomorrow's trigger can still deliver its request to the single app instance. Launch messages and startup exceptions are saved in `data/logs/scheduled-YYYY-MM-DD.log`.

Scheduled outcomes are stored in the `scheduled_runs` table in `data/applications.sqlite3` and shown in Activity. Daily application limits still stop and report normally. Daily-limit notices are non-modal so an unattended notice cannot block the next scheduled day. The next run refreshes LinkedIn before checking its current limit; uncertain submissions remain protected from retries.

## Quant and newest-first priority

The main screen always shows **Confirmed applications by this app — Today (London) / All time** above the tabs. Counts refresh during runs and at least every five seconds, persist across restarts, and use the same confirmation ledger as Daily reports. Already-applied discoveries, manual marks and uncertain submissions are excluded. The counter stays visible alongside cooldown and completion messages.

In **Job filters**, **Continue until LinkedIn daily limit or no eligible jobs** overrides the local submission cap for manual and scheduled runs. It also keeps respecting repeated temporary limits with 10-minute waits instead of stopping after two pauses. Missing/covered Easy Apply buttons, unrecognized pre-submit steps, unanswered questions and pre-submit browser timeouts leave the affected job for attention and continue to the next queued role. Login/verification requirements, browser disconnection and uncertain submissions still stop the run. Exhausting eligible jobs is reported separately; only a detected LinkedIn daily-limit notice produces **Today's complete**.

In **Job filters**, enable **Prioritize quant / quantitative roles** and **Prioritize last 24 hours**. Collection and automatic runs search LinkedIn's **Past 24 hours** filter first (quant, then the broader saved search), then repeat with **all dates**. Each pass uses the configured scan limit. Older roles remain eligible. The queue ranks the last 24 hours first, quant roles first within each age group, then newer posting dates and retry priority. When a posting date is unreadable, presence in the filtered search is used as recent evidence for up to a day; discovery alone does not establish recent posting. Other undated jobs use first-discovered time to order them within the older/unknown group. Relative posting ages are approximate. A retry never changes the original discovery timestamp. The application queue displays the same ordering.

AI still uses saved answers before generating a new answer. **Maximum AI calls per run** counts model requests, including correction attempts. Reaching it now changes the visible AI status; it does not disable saved answers. Restarting auto apply resets the request counter.

## Needs answers inbox

The **Needs answers** tab lists unanswered questions from blocked applications, sorted by the number of distinct jobs asking each question. Repeated retries count once. Existing question notes are imported automatically; new forms record the field type, available options and length limit. Browser errors, unlabelled controls and optional fields are not answer prompts.

Select a question, enter your answer, and click **Save answer and requeue ready jobs** while auto apply is stopped. The answer is saved locally in **Saved answers**, takes priority over AI and fallback defaults, and is reused for the same question (ignoring case, whitespace and required-field stars). The resolved question disappears. Jobs whose other recorded questions are also answered return to the queue ahead of ordinary queued listings; submission starts with **Start auto apply**. Manually requeued jobs receive the same retry priority. Different question wording remains separate to avoid mixing eligibility or consent questions. If a future form rejects a saved answer or changes its options, the question can return for correction. You can edit saved answers later in **Saved answers**.

## Local AI without OpenAI charges

**LLM usage** shows each new model request: time, provider/model, question, role, generated answer, raw response, validation/error outcome, duration, and input/output token counts when reported. Select a row for details; filter by London date or export the selected date's complete history to CSV. The tab refreshes every two seconds while visible and is also accessible from **AI answers → View LLM usage**. Generation, correction, and motivation evidence checks are separate requests. An accepted answer has passed validation; it does not confirm form filling or application submission. Saved answers and cached answers are not new model requests. Unknown token counts are shown as unknown, not estimated usage or cost.

Request history stays in `data/llm_usage.sqlite3`, including failed requests and rejected drafts. It contains application answers and should be treated as personal data. It does not store API keys, headers, full prompts or the full CV. Existing `ai_answers.jsonl` entries are imported once as **historical answers**, clearly separated from newly tracked request totals because earlier failures and review calls were not logged. Interrupted requests are marked on the next app start.

**AI answers → Local Ollama** is the default provider. It runs `qwen3:4b-instruct` on this PC, using your CV, saved facts and the current job to answer questions. It needs no API key and never falls back to a paid provider. OpenAI remains an explicit optional provider. Local inference still uses your computer's memory, GPU and electricity; it does not guarantee correct answers.

Motivation and cover-letter questions can be drafted from documented skills and the role context, including questions phrased “in terms of skill set”. Such wording is distinct from accepting contractual terms. Numeric word limits in the question (for example, “300 words or less”) are enforced separately from character limits. Motivation drafts also receive a second model check against the CV and saved facts without the job requirements; unsupported claims trigger one correction attempt. Only an accepted draft is filled and audited. These checks use the selected provider and count toward the run's AI-call limit; they reduce, but cannot eliminate, factual mistakes.

For a new installation, run `powershell -NoProfile -ExecutionPolicy Bypass -File .\SetupLocalAI.ps1`. This downloads the official Ollama Windows runtime (with a pinned SHA-256 check) and the approximately 2.5 GB Qwen model. Downloads require internet; inference runs on `127.0.0.1:11435`, with cloud inference disabled. The project stores the runtime and models in `data/ollama/`, starts its local server automatically when needed, and releases the loaded model after five idle minutes. Server errors are in `data/ollama/server.log`.

Enable **Generate and fill unanswered questions from my CV**, select **Local Ollama**, and use **Test AI connection**. A verified response shows the selected model and time. Save your settings, then start auto apply. Saved answers and contact facts are filled first; other supported questions use the selected model. An answer that fails format or evidence validation gets one model correction attempt with validation feedback, within the configured AI-call limit. Missing facts, consent questions and provider failures do not trigger repeated guesses. The optional **Use No for unsupported experience/qualification questions** preference first asks the model to check your CV and saved facts, then uses No for unsupported affirmative screening questions, or 0 for years-of-experience fields. It only selects an exact compatible option. Defaults are recorded as `user_authorized_default` in the audit, not as CV evidence, and are not added to your saved facts. Consent, legal declarations, salary and personal decisions remain excluded; model outages do not trigger the fallback. Saved facts are supplied as readable question: answer lines so numeric answers can cite their exact supporting fact. Generated answers must pass the same evidence, option and field-format checks as OpenAI answers. Missing personal facts or preferences mark that job as `needs_input` and the run continues to the next queued job. The unanswered question is saved in its note.

In **Saved answers**, **I hold no security clearance** answers No to current possession questions about SC, DV, CTC and security clearance. It does not infer eligibility or willingness to obtain clearance. Exact saved answers take priority. Job-specific work-location preferences should be saved under the actual question wording.

**Saved answers ? I am willing to relocate anywhere** answers common relocation-willingness questions for any destination and is included in model context. Exact saved answers take priority. It does not infer relocation dates, self-funded moving costs, work authorization or existing residence.

Question blockers before submission are recorded as `needs_input` with the reason and the run continues; they do not count toward the confirmed-application limit. Login/verification problems, navigation failures and uncertain submissions still stop the run. Platform rate limits retain their cooldown and daily-stop behavior.

## Updated workflow: uploaded resume and CV-based AI

The app can **use the first resume already uploaded to LinkedIn** and generate answers using your CV through local Ollama or the optional OpenAI Responses API. These are separate inputs: your local CV supplies AI context; the selected LinkedIn resume is the document sent to the employer. Verify that the first uploaded resume is the one you want employers to receive.

The old blanket “Could not reliably read title, company, location and description” skip has been removed. Job reading now waits for the rendered application page and tries additional DOM selectors and matching JobPosting structured data. Enable **Continue when job metadata is missing** to attempt Easy Apply even when these fields cannot be read. This allows uncheckable filters to pass; known title/location/company/description mismatches still exclude a job. A missing Easy Apply button, login challenge or unsupported form still stops for attention.

After updating, **close and restart the app without saving from the old window** to load the new settings. If you explicitly select **OpenAI**, enter its API key in the masked field (session only), or launch the app with `OPENAI_API_KEY` in its environment. Use **Test AI connection** to check the selected provider. The optional OpenAI model defaults to `gpt-4.1-mini`.

The AI status is visible above every tab and in **AI answers**, and identifies the selected provider. It distinguishes an untested configuration, a request in progress, a verified response (model and time), and a failed request. OpenAI additionally reports missing credentials. Changing the provider, relevant key or model clears verification. **Test AI connection** generates a CV-based sample; Activity shows the result. An OpenAI key typed in the app must be entered again after restarting; local Ollama needs no key. Known contact details work without AI.

UK phone numbers are formatted locally. Save the international number in Profile, for example `+44 7700 900123`. For supported phone country-code selects, the app selects **United Kingdom (+44)** and fills `7700900123` in the separate number field. If the field requires a leading zero through its constraints, example placeholder or immediate validation, it uses `07700900123`. Without a separate country-code field it prefers the full international number, adapting to a required domestic format. It does not duplicate +44, truncate numbers or ask OpenAI to decide the number. An ambiguous country option or rejected format marks that job for inspection and continues to the next queued job. Residence country is handled separately.

Only when OpenAI is selected are CV text and relevant job information sent to OpenAI. Its usage is billed to your API account. That request uses `store=false`; this is not a promise of zero retention. There are no OpenAI calls in local mode, simply from opening the app, or from importing the CV. API keys are not written to settings, prompts, or answer logs.

Answers follow this order:

1. Your exact saved answer or basic profile field.
2. If enabled, a tailored answer from the selected provider, supported by your CV and saved facts.
3. Pause if evidence is missing, the model refuses, the API fails, a field is unsupported, or the question needs an explicit personal decision.

Work authorization, sponsorship, salary expectations, consent, sensitive demographic answers and similar personal decisions require your saved answers. Experience/skills/project answers can be generated from documented evidence; a skill listing alone does not establish a number of years. The CV and employer text are treated as data, not instructions. The model receives no tools and cannot execute document instructions. Generated answers are checked against exact offered options, numeric/length constraints and verbatim evidence quotes. This reduces unsupported answers but does not guarantee perfect interpretation; inspect `data/ai_answers.jsonl` and your submitted applications.

There is a configurable **30-call limit per run** by default. Repeated questions are cached within a run using the CV, saved facts, model, job and question, so tailored answers are not reused across different jobs. Accepted answers, evidence, model, response ID and usage are logged in `data/ai_answers.jsonl` without the API key. This is personal data, like the rest of the `data` folder.

## Open the app

Dependencies are installed in this project's `.venv`. **Double-click `Start.cmd`** in this folder, or use PowerShell:

```powershell
cd C:\path\to\auto_easy_apply
.\Start.ps1
```

Or run `.venv\Scripts\python.exe -m easy_apply`. For a new installation, run `Setup.ps1` first. The setup script accepts `-PythonPath` if your Python installation differs. Python 3.11+ with Tk and Microsoft Edge are required. This version targets Windows and English-language LinkedIn pages.

1. Enter your name, email, phone and address details in **Profile**. Choose the first uploaded LinkedIn resume or a local resume file. Import your PDF/text CV in **AI answers** for tailored answers.
2. Set keywords, location, included/excluded title phrases, excluded companies, optional required description phrases, remote preference and per-run application limit in **Job filters**. Save settings.
3. Click **Open LinkedIn / sign in**. Sign in yourself in the Edge window, including any verification. The app has a separate browser profile; it does not read your usual Edge profile or request your password.
4. Click **Collect jobs to database** first. This collects the accessible results for your saved search through up to **40 pages / 5,000 new jobs**, until results end or repeat. This full collection ignores the smaller automatic-refill batch size. Each listing is committed to SQLite immediately with its URL, title, company, available location and applied status; no applications are opened or submitted by collection. The queue shows database totals and fills during the scan. You can also paste individual LinkedIn job URLs.
5. Click **Start auto apply**. This authorizes submission under your filters and missing-metadata preference, up to your per-run limit. It processes queued jobs one after another. If the queue is empty at startup or becomes empty after applications, it automatically searches once using your saved filters and continues with newly queued jobs. This search can inspect up to 40 pages (previously five), stopping earlier at the configured new-job limit or the end of results. The final status explains when there are no queued title matches; the queue summary separates all saved searches from titles matching the active filters. It fills saved facts and enabled CV-grounded AI answers, advances through supported Easy Apply forms, and clicks Submit application automatically. New submissions require a visible application-sent confirmation. If LinkedIn already shows the job as applied, the app records that existing application and opens the next queued job automatically. The status line and Activity show progress and why the run ends.
6. Unknown or invalid required answers mark the job `needs_input` and automatically move to the next queued job. To revisit it later, read the exact label in **Activity** or the selected job's note, add your answer in **Saved answers**, save, and use **Requeue after fixing answers**. Restart the run. You can also finish an unsupported application manually and mark it applied.

**LinkedIn prohibits third-party automation and may restrict accounts that use it.** See [LinkedIn's policy](https://www.linkedin.com/help/linkedin/answer/a1341543). This app does not bypass login verification, CAPTCHAs, rate limits or detection, and makes no claim that automation is permitted or account-safe. No applications are sent merely by opening the desktop app.

## Saved answers

Answers are a JSON object of exact question wording and exact answer/option wording. The UK phone country code is normally inferred from your international phone number; a saved option can disambiguate matching +44 entries. For example:

```json
{
  "Phone country code": "United Kingdom (+44)"
}
```

Text answers respect both HTML length limits and accessible character counters. A known GBP salary that exceeds the limit is entered as its numeric amount (for example, `At least GBP 75,000 per year.` becomes `75000`); numeric salary fields also receive the amount alone. Your stored salary facts remain unchanged. Other long answers are flagged rather than silently truncated. No currency conversion is inferred.

On opening an application, the app waits up to 15 seconds for stable fields and a Next/Review/Submit action; a dialog containing only Dismiss is treated as still loading. After Next or Review, the app waits for the next form step to finish rendering. Visible validation errors or a page that fails to advance mark the job `needs_input` and continue the queue, rather than repeatedly clicking the same button.

Existing applications are also recognized in the newer job page's separate **Application status** card, including **Application submitted** below the header. These become **already applied**, use no new-submission allowance, and the queue continues even when there is no Easy Apply button. Status text in descriptions, recommended jobs, hidden cards, and unrelated panels is ignored.

The auto-apply queue uses your current included-title filters. Jobs with known unrelated titles remain saved for another search. When matching titles run out, the app refreshes the current search once immediately instead of opening every unrelated saved job first. Untitled listings still receive a live title check. Your configured submission cap still applies.

Only required fields are filled: a label with an asterisk, an HTML `required` attribute, or `aria-required="true"` marks a required question. Optional fields such as Photo, Location, cover letters, uploads and radio questions are skipped even when a saved answer exists. They do not call the model or block the application. Existing optional text and selections are left unchanged; optional prechecked checkboxes are unchecked.

Save `Do you have a PhD?` as `No` (or your actual answer) to cover equivalent PhD/Doctor of Philosophy possession and completion questions without a model call. There is no default degree answer. This fact also goes to the local model for other wording; it does not answer combined questions such as “PhD or Masters” by itself. New LinkedIn radio layouts with empty native labels read the adjacent option text and click the associated visible label, then verify the selection.

Name, email, phone and address fields have explicit label aliases. Required city autocomplete fields can read paragraph labels in LinkedIn's newer layout and select a matching suggestion using your saved city and country; optional city fields remain untouched. Other required questions use your saved answers or the enabled AI workflow above. Normalization ignores letter case, whitespace, trailing question marks/colons and required-field asterisks. Do not add broad guesses: work authorization, sponsorship, salary, eligibility, demographic answers and legal consents have no defaults. Experience/qualification defaults require the explicit AI preference described above. Required prefilled text is still checked against your saved facts or generated answer. Radio options are exact-matched. Required consent needs your explicit saved yes/no answer. Hidden native checkboxes use their visible ARIA wrapper or associated label, including the final review's Follow-company checkbox. The app verifies the checked state afterward. A checkbox that cannot be changed is recorded as needing attention and other queued jobs continue.

Standard input, select, textarea and radio controls are supported. Custom widgets, rich-text questions, unknown country-code selectors or changed LinkedIn page layouts can require manual work. In first-uploaded mode, the first recognized resume card/radio is selected and its selected state verified; it does not upload the local file. If no saved resume can be recognized on a required resume step, that job is marked `needs_input` and the run continues. In local-file mode, the configured resume is uploaded instead. Required unidentified uploads mark that job for attention and allow other queued jobs to continue. Do not edit the browser manually while a run is active; press Stop first.

CV-only steps also recognize filenames beside radio buttons, filenames referenced through accessibility labels, unnamed resume radio groups and custom radio controls. All recognized CV options are excluded from ordinary question answering; the app verifies selection of the first visible CV before proceeding. This requires no model call. Resume detection shares the same labels across required-field checks, selection and review, including `Lebenslauf`, `Curriculum`, `Curr?culum`, `Curr?culo` and `Curriculum Vitae`. It also recognizes a document picker with a different heading when LinkedIn's standard resume-upload instructions appear in the same section beside file choices. It does not classify every PDF upload as a CV. Cover-letter choices and unrelated unanswered questions remain separate. After updating from a version that stopped with **Unlabelled radio question** on a CV-only page, restart the app, select that blocked job and use **Requeue after fixing answers** before starting again.

The newer layout nests a native radio input inside a `role="radio"` wrapper and uses a paragraph for `Resume*`. These are treated as one CV choice, with the filename read from the wrapper or adjacent card. This layout was verified on a live application through the Review step, without submitting it, and is covered by a regression test.

The final review's read-only résumé summary is accepted when a document filename is displayed, rather than being treated as a fresh selection step. Missing required documents still block that application; optional résumé sections are skipped. Additional questions can use paragraph labels and hidden native radio inputs: the app reads the visible wrapper's Yes/No text, clicks that wrapper and verifies the native checked state.

## Filters and job history

- Search keywords/location are sent to LinkedIn with its Easy Apply filter. Remote-only adds the remote search filter.
- Before each application, the app reads title, company, location and description and checks local filters again. Only metadata needed by a configured filter is required in strict mode; missing-metadata mode explicitly permits uncheckable filters.
- Queued jobs with known titles matching your current title filter are prioritized. A saved search-listing title/company can supply metadata missing from the matching job page. An included-title filter requires a readable live or saved title even in missing-metadata mode.
- Title inclusion matches **any** comma-separated phrase; exclusions match **any** phrase. Required description phrases must **all** appear.
- Location is a case-insensitive text match against the job header. Use a phrase actually present in postings (e.g. London). This is not a geographical-radius model.
- Remote-only excludes a recognized non-remote workplace. An unknown workplace is excluded in strict mode and permitted in missing-metadata mode.
- The default cap is **5 confirmed submissions per run**, configurable from 1 to 50. There is no scheduling, background unattended launch, salary parsing or AI ranking in this version.
- Each run can refill its queue with **one automatic search**, checking up to five results pages with the same filters. The scan limit counts newly queued jobs. Search skips existing IDs, records recognized Applied badges on individual result cards, scrolls nested result panels, waits for delayed cards, and uses visible Next/page controls. Existing uncertain submissions remain protected. If there are no further pages, a page repeats, or the scan reaches its bounds, it finishes with a message explaining the result. Activity reports each queued job and counts of already-applied/existing results so an empty queue has an explanation.
- The collector supports both traditional job links and the newer `/jobs/search-results/` layout, whose cards use `componentkey="job-card-component-ref-ID"` instead of links. It refreshes metadata as virtualized cards finish rendering. It records each scan in the SQLite `scans` table, including partial scans. Repeating a collection enriches the existing listings without resetting application history. The collection bounds do not guarantee every LinkedIn job is accessible.
- IDs are deduplicated. `applied`, `submitting` and `unverified` jobs cannot be automatically requeued.
- **Submitted by app** counts only submissions with an app-observed confirmation. **Already applied on LinkedIn** counts pre-existing applications discovered on job cards/pages, not new submissions. These are separate totals and row labels. Manual confirmations and records with an unknown source are also shown separately. The database and CSV retain `application_source`; older records are classified only when their saved notes establish the source. These totals cover this local database, not your entire LinkedIn application history.
- A visible ?No longer accepting applications?, ?Not currently accepting applications?, or supported closed/expired notice in the current job?s application area marks it `skipped` and continues to the next queued job. Closed jobs do not consume the submission limit. Both traditional headers and the newer LinkedIn job-details polite/assertive live regions are supported; notices in descriptions, recommendations and hidden elements are ignored. Already-applied history takes priority over a closure notice.
- Jobs with a recognized visible applied status in LinkedIn's job header/application area are recorded as `applied` with a “No new submission” note and skipped. They do not consume the new-application limit. Status text in descriptions, recommendations or hidden elements is ignored. If an earlier run stopped on such a job with “No visible Easy Apply button”, select it and click **Requeue after fixing answers** to let the updated app check it again.
- Before clicking Submit, status is committed to SQLite as `submitting`. An interruption or uncertain result becomes `unverified`; the entire run stops rather than resubmitting. Verify manually in LinkedIn. The app intentionally has no one-click retry of uncertain submissions.
- Stop is checked between browser operations. A click already sent cannot be recalled; an in-flight operation may take several seconds to finish.

When a recognized **applying too fast**, **applying at a fast pace**, or **Easy Apply is temporarily paused** warning appears, the app pauses for **10 minutes**, or longer if LinkedIn explicitly requests a longer interval in seconds/minutes/hours. A live MM:SS countdown (10:00, 09:59, ...) replaces the message in the main status line and updates every second. Activity records the start and minute-level progress without adding a log line every second. Stop remains available during the pause. After waiting, it reloads and checks the page before continuing; a persistent warning allows at most two pauses in capped mode. With Continue until LinkedIn daily limit enabled, it keeps waiting and rechecking instead. These pauses do not guarantee that LinkedIn's restriction has expired.

A recognized **daily application maximum** message, including **You reached today’s Easy Apply limit**, stops the run immediately and leaves remaining jobs saved for a later run. The desktop shows a notification and keeps **Today's complete — LinkedIn daily limit reached** in the status after the worker stops. Reopening the app on the same London date restores this status; yesterday's completion is not restored. Easy Apply entry detection supports both buttons and LinkedIn links to the current job, including entries that open a limit notice. Activity and a timestamped JSON report under `data/reports/daily-limit-*.json` record the LinkedIn message, detection time, confirmed submissions in this run (when known), queued count, and any unverified submissions. This is separate from the app's configured per-run submission cap. It does not schedule an automatic restart. If either limit appears after Submit was clicked, that submission remains `unverified`. After a temporary cooldown, the app can continue only if the job page confirms it was applied; it never blindly retries that submission. If confirmation is still missing, inspect it manually. Limits are detected from visible English-language messages; wording/layout changes may require an update.

The app scrolls the application modal and its nested panels to reach footer controls, including on short browser windows. It recognizes supported Next/Review/Apply/Submit labels from visible text and accessibility labels, and includes footers outside the inner form panel. It checks that an action is reachable before clicking. A disabled or covered button stops with a specific note and remains retryable; the app does not force-click through an overlay. Submission status is recorded only after the button passes this check and immediately before the actual click. An unrecognized step now lists the visible button labels in its note.

The initial Easy Apply control is checked by visible text and accessibility labels, with LinkedIn's current `job-apply-button` marker preferred. After reading job metadata, the app retries for up to 12 seconds while the control loads or is replaced, and checks reachability before opening the form. Description text, recommended job cards, external Apply links and hidden controls are excluded. Late applied/closed notices still take precedence.

The queue supports CSV export. A single-instance lock prevents two copies from sharing the application history and browser profile simultaneously.

## Local storage

**Job filters → Exclude senior and leadership roles** excludes Senior/Sr., Director, Manager/Mgr., Principal (including principle), Staff, Head, Lead, Team Leader, Chief, President/VP and executive titles such as CTO. Saved pending titles are checked before opening the job; the live title is checked again before applying. Mentions in descriptions or company names alone do not exclude a job. Phrases such as Head Office and Lead Generation are not leadership matches. Matches become `skipped` with a reason, while submitted and uncertain application history is preserved. This preference also applies to scheduled runs.

**Job filters → Full-time permanent only** excludes contract/contractor, fixed-term/FTC, temporary, freelance, interim, part-time, internship and apprenticeship roles, plus advertised day/hour rates and IR35 engagements. A Full-time badge does not override a Contract badge or contract terms in the description. The app checks saved metadata and the live job before opening an application, marking matches `skipped` while preserving submission history. Missing employment metadata is not proof that a job is permanent; the filter excludes explicit conflicting terms it can read. Contract-related skills such as smart contracts do not by themselves exclude a role.

**Job filters → Exclude jobs that require SC clearance** removes explicitly SC-required roles from pending applications. Saved listings are checked when settings are saved, after collection, and before processing the queue; the live description is checked again before applying. Matches remain in history as `skipped` with an SC-clearance reason. Optional clearance, eligibility to obtain clearance, and a screening question alone do not exclude a role. Existing application history is preserved.

`data/settings.json` contains your profile, CV text, preferences and saved answers. `data/applications.sqlite3` contains the queue, statuses and job metadata. `data/browser_profile/` contains the separate Edge session, including login cookies. These files are local and excluded from Git, but **not encrypted by this app**. Protect the folder as personal data. Local resumes stay at their selected path and are only uploaded in local-file mode during application steps. Enabled AI sends CV/context to OpenAI; application data and the chosen resume go to LinkedIn/employers. No analytics service is used.

`data/diagnostics/latest-search.json` records the last page's title, URL, headings and DOM markers so an empty scan can be diagnosed. It does not contain cookies or form input values. Diagnostic data remains local. For collection without the desktop UI, close the desktop app and run `.venv\Scripts\python.exe -m easy_apply.collect`; it reuses the saved browser session and only collects jobs. Login or application-limit warnings stop this command.

## Validation and limits

Run the unit tests:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Run offline browser integration tests in installed Edge:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s browser_tests -v
```

Browser tests use simulated pages with network requests intercepted; they do not sign in to LinkedIn or send real applications. Live selectors and confirmations need validation in your authenticated English-language LinkedIn account. LinkedIn frequently changes page structure; failures stop for inspection rather than indicating success. A working simulated flow does not establish compatibility with every live application.

The hidden-window desktop smoke test is `.venv\Scripts\python.exe -m unittest discover -s ui_tests -v`.

Implementation uses [Playwright browser channels](https://playwright.dev/python/docs/browsers) and its [persistent browser contexts](https://playwright.dev/python/docs/api/class-browsertype#browser-type-launch-persistent-context).

AI implementation follows the official OpenAI [Responses structured outputs documentation](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses) and [GPT-4.1 mini model documentation](https://developers.openai.com/api/docs/models/gpt-4.1-mini). API tests are mocked until a real API key is supplied; no live AI generation is claimed without a successful connection test.
